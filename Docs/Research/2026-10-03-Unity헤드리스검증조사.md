# Unity 헤드리스 검증 조사 — U1~U5 를 AI 가 배치모드로 확인하는 길

2026-10-03 · 조사 · DataTool

## 0. 결론 먼저

**된다. 스크래치 빈 프로젝트에서 U1~U5 를 사람 손 없이 다 통과시켰다.**

| # | 무엇 | 어떻게 봤나 | 결과 |
| --- | --- | --- | --- |
| U1 | 생성 `.cs` 컴파일 · 소스 제너레이터 | 배치모드 열기 + EditMode 시험이 생성 어셈블리 안 타입을 리플렉션으로 셈 | **오류 0** · `GeneratedMessagePackResolver` 와 포매터 셋이 생겼다 |
| U2 | Go 가 구운 파일을 C# 이 읽나 | EditMode 시험이 `StreamingAssets/gamedata.bytes` 를 `Load` | **통과** |
| U3 | 한글 · float · enum · 기본값 · ref | 같은 시험에서 값 대조 | **통과** |
| U4 | 해시가 다르면 `GameDataException` | 구운 바이트의 해시 16글자를 `0` 으로 덮고 `Assert.Throws` | **통과** |
| U5 | IL2CPP 플레이어 | `-executeMethod` 로 Win64 IL2CPP 빌드 → 플레이어를 `-batchmode -nographics` 로 돌려 로그 대조 | **통과** (스트리핑 Minimal · High 둘 다) |

**추천 길** — MessagePack 은 **NuGetForUnity 없이 dll 다섯 장 + 분석기 한 장을 `Assets/Plugins/` 에 넣는다.**
git URL 패키지(`MessagePack.Unity`)는 **우리 데이터에는 필요 없다** (Unity 타입을 안 쓴다 — 빼고도 U1~U5 가 다 됐다).
판은 **3.1.9** 로 고정한다 (`roundtrip-cs` 와 같은 판).

**밟은 함정 하나** — 의존성에서 `System.Runtime.CompilerServices.Unsafe 6.0.0` 을 빼먹으면
컴파일은 되는데 **float 열을 읽을 때 `FileNotFoundException`** 이 난다. 컴파일 오류 0 으로는 못 잡는다 — U2 시험이 잡았다.

**DataTool 쪽에 넘길 것 둘** — ① `Unity/README.md` 1번(설치)이 실제보다 무겁고 Unsafe 를 모른다.
② `GameDataTables.Deserialize` 가 **표를 다 읽은 뒤에** 해시를 본다. 스키마 꼴이 바뀐 채 안 구우면
`GameDataException` 대신 MessagePack 예외가 먼저 날 수 있다 (4장).

## 1. MessagePack 을 사람 없이 넣는 길

### 1-1. 공식 조건

- 공식 README : **Unity 2022.3.12f1 이상** (IL2CPP 를 C# 소스 제너레이터로 받치는 것이 그 판부터).
  설치는 NuGetForUnity 로 `MessagePack` + git URL 패키지 둘을 하라고 적혀 있다.
  근거 : <https://github.com/MessagePack-CSharp/MessagePack-CSharp#unity-support>
- 우리 에디터 6000.3.23f1 은 조건을 넘는다. 에디터 Roslyn 은 **4.3.1** (`Editor/Data/DotNetSdkRoslyn/csc.dll -version`)
  이고, 분석기 패키지가 `analyzers/roslyn4.3/` 판을 주므로 딱 맞는다.
- NuGet 최신은 3.1.10 이지만 **3.1.9 로 고정한다.** `roundtrip-cs` 가 그 판으로 57건을 봤기 때문이다.

### 1-2. 후보 셋

| 길 | 사람 손 | 새 설치 | 판정 |
| --- | --- | --- | --- |
| **(a) nupkg 를 받아 dll 을 `Assets/Plugins/` 에** | 0 | 없음 (curl + unzip) | **추천 · 실제로 해 봄** |
| (b) NuGetForUnity.Cli (`dotnet nugetforunity restore <프로젝트>`) | 0 | `dotnet tool install NuGetForUnity.Cli` — **사용자 승인 필요** | 후보만. 에디터 패키지 NuGetForUnity 와 `packages.config` 도 같이 깔아야 한다. 분석기 라벨 처리는 문서에 없다 |
| (c) NuGetForUnity 에디터 UI | 있음 | 에디터 패키지 | 지금 README 의 길. AI 가 못 한다 |

### 1-3. (a) 에 들어가는 것 — 실제로 넣은 목록

`.nuspec` 의 netstandard2.1 의존성을 따라가며 받았다. 전부 `nuget.org` 의 `v3-flatcontainer` 에서 `curl` 로 받는다.

| 파일 | 패키지 · 판 | nupkg 안 자리 |
| --- | --- | --- |
| `MessagePack.dll` | MessagePack 3.1.9 | `lib/netstandard2.1/` |
| `MessagePack.Annotations.dll` | MessagePack.Annotations 3.1.9 | `lib/netstandard2.0/` |
| `Microsoft.NET.StringTools.dll` | Microsoft.NET.StringTools 17.11.4 | `lib/netstandard2.0/` |
| `System.Collections.Immutable.dll` | System.Collections.Immutable 8.0.0 | `lib/netstandard2.0/` |
| `System.Runtime.CompilerServices.Unsafe.dll` | System.Runtime.CompilerServices.Unsafe 6.0.0 | `lib/netstandard2.0/` ← **빼먹으면 실행 때 터진다** |
| `Analyzers/MessagePack.SourceGenerator.dll` | MessagePackAnalyzer 3.1.9 | `analyzers/roslyn4.3/cs/` |

- `System.Memory` 는 안 넣었다. Unity 의 .NET Standard 2.1 프로필에 이미 있다.
- 분석기 패키지의 `MessagePack.Analyzers.CodeFixes.dll` 은 안 넣었다 (IDE 용 · Workspaces 를 찾아 경고만 낸다).
- 분석기 dll 은 **`.meta` 를 손으로 써서 같이 넣는다.** Unity 가 처음 가져올 때 이 `.meta` 를 그대로 쓴다.
  요점은 셋 — `labels: [RoslynAnalyzer]` · 모든 플랫폼 `enabled: 0` · Editor 도 `enabled: 0`.
  넣은 꼴은 scratchpad `UProbe/Assets/Plugins/MessagePack/Analyzers/MessagePack.SourceGenerator.dll.meta`.
- 결과 확인 : 생성 어셈블리의 컴파일 응답 파일(`Library/Bee/artifacts/…/MyGame.Data.rsp`)에
  `-analyzer:"Assets/Plugins/MessagePack/Analyzers/MessagePack.SourceGenerator.dll"` 가 실려 있다.
  asmdef 가 없는 폴더(`Plugins`)의 분석기라 프로젝트의 모든 어셈블리에 걸린다.
- 나머지 dll 은 기본 가져오기(모든 플랫폼 켬)로 둔다. 생성 asmdef 가 `overrideReferences: false` 라
  자동 참조로 `MessagePack.dll` 을 본다 — **생성 asmdef 는 손댈 것이 없다.**

### 1-4. git URL 패키지는 빼도 된다

- `MessagePack.Unity` 패키지가 하는 일은 **`UnityResolver`(Vector3·Color 같은 Unity 타입 포매터)를 `DefaultOptions` 에 얹는 것**뿐이다
  (`MessagePackInitializer.cs` · v3.1.9 태그).
- 우리 행 클래스는 `string`·`int`·`float`·`bool`·배열만 쓴다. 생성 포매터는 `StandardResolver` 가 찾는다.
- 실측 : manifest 에서 패키지를 뺀 채로 EditMode 3/3 통과 · IL2CPP 빌드·실행 통과 (2장·3장 로그).
- 넣고 싶으면 `Packages/manifest.json` 에 한 줄이면 된다 (배치모드에서 git 으로 받아짐 · 판 고정 `#v3.1.9`).
  `"com.github.messagepack-csharp": "https://github.com/MessagePack-CSharp/MessagePack-CSharp.git?path=src/MessagePack.UnityClient/Assets/Scripts/MessagePack#v3.1.9"`
- 덧 : 패키지를 넣은 판에서도 IL2CPP 플레이어가 찍은 `DefaultOptions.Resolver` 는 `StandardResolver` 였다.
  `UnityResolver` 가 안 얹힌 까닭은 확인 안 했다 (우리 일엔 상관없다 · 5장).

## 2. U1~U4 — EditMode 시험

### 2-1. 꼴

```
Assets/Tests/EditMode/
  DataProbe.Tests.EditMode.asmdef   references: UnityEngine.TestRunner · UnityEditor.TestRunner · <생성 asmdef 이름>
                                    precompiledReferences: nunit.framework.dll · MessagePack.dll · MessagePack.Annotations.dll
                                    overrideReferences: true · includePlatforms: [Editor] · defineConstraints: [UNITY_INCLUDE_TESTS]
  GameDataTests.cs                  시험 셋 (아래)
```

- 생성 asmdef 이름은 스키마 `namespace` 값이다 (시험 자료는 `MyGame.Data`). 시험 asmdef 는 그 이름을 참조한다.
- `test-framework` 1.6.0 이 manifest 에 있어야 한다. OfficinaTest 에는 이미 있다.

| 시험 | 하는 일 |
| --- | --- |
| `U1_SourceGeneratorMadeFormatters` | `typeof(ItemRow).Assembly` 안에서 `GeneratedMessagePackResolver` 와 `ItemRowFormatter`·`MonsterRowFormatter`·`DropRowFormatter` 를 찾고, 리졸버 `Instance.GetFormatter<ItemRow>()` 가 null 이 아닌지 본다 |
| `U2_U3_LoadBakedAndCompareValues` | `StreamingAssets` 의 구운 파일을 `GameDataLoader.Load` → 행 수 · 한글 · int · float32(0.05·0.01) · bool · enum · 기본값(0 · 빈 배열 · `[1]`) · asset 문자열 · `Get<T>` 대조. `roundtrip-cs/Program.cs` 의 일부를 옮긴 것 |
| `U4_SchemaHashMismatchThrows` | 구운 바이트에서 ASCII `schemaHash` 16글자를 찾아 `0` 으로 덮고(길이가 같아 자리가 안 밀린다) `Assert.Throws<GameDataException>` — `roundtrip-cs` README 의 수법을 메모리에서 한다 |

생성된 실제 이름 (로그) : `MessagePack.GeneratedMessagePackResolver` ·
`MessagePack.GeneratedMessagePackResolver+MyGame+Data+ItemRowFormatter` 등. **네임스페이스가 `MessagePack` 이다** — 생성 어셈블리마다 하나씩 생긴다.

### 2-2. 명령 · 종료 코드 · 결과 파일

```powershell
# 열기만 (컴파일 확인) — 컴파일 오류가 있으면 로그에 "error CS" 가 찍힌다
Unity.exe -batchmode -nographics -quit -projectPath <프로젝트> -logFile <log>

# EditMode 시험 — -quit 을 붙이지 않는다 (시험이 끝나면 스스로 나간다)
Unity.exe -batchmode -nographics -projectPath <프로젝트> -runTests -testPlatform EditMode -testResults <xml> -logFile <log>
```

| 종료 코드 | 뜻 (실측) |
| --- | --- |
| 0 | 다 통과 |
| 2 | 시험이 하나라도 실패 (Unsafe 빠진 판에서 실제로 봤다) |

- 결과는 NUnit 3 XML. 판정은 첫 줄 `<test-run … result="Passed" total="3" passed="3" failed="0">` 하나로 충분하다.
  실패 이유는 `<test-case … result="Failed">` 아래 `<failure><message>` 와 `<stack-trace>` 에 있다.
- `Debug.Log` 는 `-logFile` 로그에 남는다. 시험 안에서 `PROBE …` 처럼 머리말을 달아 두면 grep 한 번으로 뽑힌다.
- 시간 : 첫 열기(패키지 해석 + 컴파일) 16초 · 시험 판 10초.

## 3. U5 — IL2CPP 빌드와 헤드리스 실행

### 3-1. 빌드

`Assets/Editor/ProbeBuild.cs` 의 정적 메서드를 `-executeMethod` 로 부른다. 하는 일은 넷이다.

1. 빈 장면이 없으면 만들어 저장한다 (`EditorSceneManager.NewScene(EmptyScene)` → `Assets/_Probe/Probe.unity`).
   빈 프로젝트는 Build Settings 장면 목록이 비어 있어서다.
2. `PlayerSettings.SetScriptingBackend(NamedBuildTarget.Standalone, ScriptingImplementation.IL2CPP)`.
   **ProjectSettings 에서 바뀌는 것은 이 `scriptingBackend` 하나다** (빌드 메서드가 저장해 버린다 — OfficinaTest 에서 돌리면 `ProjectSettings.asset` 이 바뀐다).
   `-stripping High` 인자를 주면 `SetManagedStrippingLevel` 도 바꾼다.
3. `BuildPipeline.BuildPlayer(scenes, <out>/Probe.exe, StandaloneWindows64, None)`.
4. `EditorApplication.Exit(성공 ? 0 : 1)` — 배치모드 종료 코드로 성패를 돌려준다.

```powershell
Unity.exe -batchmode -nographics -projectPath <프로젝트> -executeMethod ProbeBuild.BuildWin64Il2Cpp -buildOut <폴더> [-stripping High] -logFile <log>
```

| 판 | 빌드 시간 | 결과 |
| --- | --- | --- |
| 첫 빌드 (Minimal) | **80초** (빌드 자체 70초) | Succeeded · 오류 0 · 경고 0 |
| git 패키지 뺀 뒤 다시 (Minimal) | 19초 (Bee 캐시) | Succeeded |
| 스트리핑 High | 55초 | Succeeded |

- IL2CPP 가 정말 걸렸는지는 산출물 `GameAssembly.dll` 과 플레이어 안 `#if ENABLE_IL2CPP` 로그로 확인했다.
- 빈 프로젝트라 빠르다. 실제 게임 프로젝트는 몇 분~수십 분으로 늘어난다 (어림 · 안 쟀다).

### 3-2. 플레이어를 헤드리스로 돌려 결과 받기

- `Assets/_Probe/ProbeRunner.cs` — `[RuntimeInitializeOnLoadMethod(AfterSceneLoad)]` 에서
  `LoadFromStreamingAssets()` → 값 여섯 개 대조 → `Debug.Log("PROBE RESULT OK")` → `Application.Quit(코드)`.
  코드 0 통과 · 1 값 어긋남 · 2 예외.
- 실행 : `Probe.exe -batchmode -nographics -logFile <log>` → **3초 만에 끝난다.** 종료 코드가 그대로 셸로 온다.

| 판 | 종료 | 로그 |
| --- | --- | --- |
| 정상 | 0 | `il2cpp=True resolver=MessagePack.Resolvers.StandardResolver` · `PROBE RESULT OK` |
| `gamedata.bytes` 를 치운 판 | **2** | `PROBE RESULT EXCEPTION … GameDataException: 구운 데이터 파일이 없다` — 실패도 코드로 잡힌다 |

### 3-3. 리졸버를 손으로 엮어야 하나 (README 5번)

**아니다 (이 판 · Win64 · Minimal/High 에서).** `StandardResolver` 가 생성 어셈블리의 `GeneratedMessagePackResolver` 를 찾아 쓴다.
`[GeneratedMessagePackResolver]` partial · `StaticCompositeResolver` 를 얹을 일이 없었다.
`Dynamic*` 리졸버(리플렉션 Emit)로 떨어졌다면 IL2CPP 에서 바로 예외였을 것이다.

## 4. DataTool 쪽에서 준비할 것 · 설계와 어긋나는 점

### 4-1. 넣는 입력

- 입력은 **`DataTool/Testdata/table/ok/`** (namespace `MyGame.Data` · 표 셋 18행 · 해시 `1db5aa5f0ede6b0a`).
  `roundtrip-cs` 와 같은 판이라 기대값을 그대로 옮길 수 있다.
- 명령 (실제로 돌린 것, 둘 다 종료 0) :

```powershell
datatool gen    --data Testdata\table\ok --out <프로젝트>\Assets\_Project\Scripts\Data\Generated
datatool export --data Testdata\table\ok --out <프로젝트>\Assets\StreamingAssets\gamedata.bytes
```

- `gen` 산출 아홉 장이 `Testdata/gen/expected/` 와 **글자까지 같았다** (`diff -r`). 구운 파일 923바이트.
- 경고가 한 줄 나온다 — `Testdata/table/Library/AssetTool/address-index.json` 이 없어 asset 검사를 건너뜀. 시험엔 상관없다.
- 쓴 `datatool.exe` 는 `0.1.0-dev (3101a64-dirty · 2026-10-01 빌드)` 다. 실측 전에 `build.ps1` 로 다시 굽는 것이 깔끔하다.

### 4-2. OfficinaTest 에 놓을 자리 (다음 작업 판)

| 자리 | 무엇 |
| --- | --- |
| `Assets/Plugins/MessagePack/` | 1-3 의 dll 다섯 + `Analyzers/` 분석기(.meta 포함) |
| `Assets/_Project/Scripts/Data/Generated/` | `datatool gen` 산출 (생성 asmdef 포함) |
| `Assets/StreamingAssets/gamedata.bytes` | `datatool export` 산출 |
| `Assets/Tests/EditMode/` | 시험 asmdef + `GameDataTests.cs` (U1~U4) |
| `Assets/Editor/ProbeBuild.cs` · `Assets/_Probe/` | U5 빌드 메서드 · 플레이어 탐침 · 빈 장면 |

시제품은 전부 scratchpad `UProbe/Assets/` 아래에 있다 (경로는 6장). 옮겨 쓰면 된다.

### 4-3. 어긋나는 점

| # | 어디 | 무엇이 다른가 | 제안 |
| --- | --- | --- | --- |
| 1 | `Unity/README.md` 1번 | 「둘 다 해야 한다」 → 실제로는 **git 패키지 없이 된다.** NuGetForUnity 대신 dll 직접 넣기도 된다 | 설치 길을 둘로 적는다 (NuGetForUnity · dll 직접). git 패키지는 「Unity 타입을 직렬화할 때만」 |
| 2 | `Unity/README.md` 1번 | `System.Runtime.CompilerServices.Unsafe` 를 모른다. NuGetForUnity 는 의존성으로 같이 받겠지만 손으로 넣으면 빠진다 | dll 목록을 적는다 |
| 3 | `Unity/README.md` 5번 · 설계 13장 위험 「IL2CPP 에서 소스 제너레이터가 안 걸린다」 | 이번 판에서 걸렸다. 리졸버 수동 등록 불필요 | 「Win64 · 6000.3 에서 확인」으로 낮춘다. 모바일 IL2CPP 는 미확인으로 남긴다 |
| 4 | `GameDataTables.Deserialize` (생성 코드) | **해시를 표를 다 읽은 뒤에 본다.** Go 는 맵 키를 정렬해 쓰는 것으로 보이고(구운 파일 키 차례가 `_meta`·`drop`·`item`·`monster` — 실측. 스키마 차례가 아니다), `_` 가 소문자보다 앞이라 `_meta` 가 늘 첫 키다. 그런데 C# 은 `drop`·`item`… 을 다 읽고 나서 비교한다. 열 타입이 바뀐 채 안 구우면 **MessagePack 예외가 먼저 난다** — 설계 13장 위험 「스키마 고치고 안 구웠다 → 뜰 때 GameDataException」이 꼴에 따라 안 지켜진다 | `_meta` 를 읽은 그 자리에서 해시를 비교해 바로 던진다. `_meta` 가 첫 키가 아니면 그것도 예외로. 생성기 수정 + 정답지 갱신 몫 |
| 5 | 설계 13장 「안 한 것」 | Unity 를 안 열었다 → 이제 연 기록이 있다 | 실측 뒤 13장에 결과 한 줄 |

U4 시험(해시만 바꾼 판)은 4번과 상관없이 통과한다 — 꼴은 그대로라 표를 다 읽고 해시에서 걸리기 때문이다.
