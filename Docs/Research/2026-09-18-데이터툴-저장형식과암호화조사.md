### 왜 JSON 인가

세 가지가 동시에 필요하다.

1. **git 이 줄 단위로 봐야 한다.** 바이너리(SQLite·xlsx)는 diff 가 「파일이 바뀜」 한 줄로 끝난다.
   merge 는 아예 안 된다. SQLite 를 git 에 넣는 방법은 있지만 — `.gitattributes` + `textconv` 로
   `sqlite3 .dump` 를 걸거나 `sqldiff` 기반 머지 드라이버를 쓰는 식 — **저장소를 쓰는 모두가 그 설정을 깔아야** 한다.
   1인 + AI 에이전트 환경에서 설정 한 겹을 더 얹는 값어치가 없다.
   (출처: [SQLite Database in Git](https://ongardie.net/blog/sqlite-in-git/) ·
   [git-sqlite](https://github.com/cannadayr/git-sqlite))
2. **AI 가 툴 없이 읽고 써야 한다.** AI 는 텍스트만 본다. SQLite·xlsx·구글 시트는 전부 중간 도구가 필요하다.
   JSON 은 열면 끝이다.
3. **열 타입·enum·참조가 표현돼야 한다.** CSV 는 전부 문자열이라 이걸 못 한다.
   JSON 은 숫자/문자열/불리언을 구분하고, 스키마는 C# 클래스에 둔다.

### 한 줄 한 행으로 쓰는 이유

JSON 을 예쁘게 들여쓰면 값 하나 고쳤을 때 diff 가 한 줄로 안 나오는 경우가 생긴다.
**행(레코드) 하나를 한 줄에** 쓰면 git diff 가 「어느 행이 어떻게 바뀌었나」로 바로 읽힌다.
JSON Lines 와 같은 생각이고, 사람도 AI 도 「몇 번 아이템 줄」로 짚을 수 있다.
JSON 은 필드 이름이 값 옆에 붙어 있어 CSV 보다 리뷰가 쉽다는 지적도 같은 맥락이다.
(출처: [JSON vs CSV](https://medium.com/@crawlbase/json-vs-csv-main-differences-8f8c144b4b43) ·
[priconne-diff](https://github.com/Expugn/priconne-diff) — 게임 데이터 변경분을 JSON 으로 추적하는 실사례)

JSON 이 그래도 충돌하면 **행마다 파일 하나**로 쪼개는 길이 있다. 「쓰는 사람마다 파일을 나누면 충돌이 사라지고,
합친 표는 코드가 만들어 낸다」는 패턴이 이미 널리 쓰인다.
(출처: [Avoid JSON file merge conflicts](https://sophiabits.com/blog/avoid-json-file-merge-conflicts) ·
[git-json-merge](https://github.com/jonatanpedersen/git-json-merge))
다만 수만 행이면 파일이 수만 개가 되어 git 도 파일 시스템도 느려진다. **기본은 테이블별 한 파일**,
잘 깨지는 표만 골라 쪼개는 걸 권한다.

### 서버 DB 는 1인 개발에 과한가 — 그렇다

근거 네 가지.

- **띄우고 돌봐야 한다.** MySQL/Postgres 는 서버 프로세스·백업·접속 정보 관리가 딸려 온다. 혼자 하는 값이 아니다.
- **git 밖으로 나간다.** 게임 코드와 데이터의 버전이 따로 놀게 된다. 「어제 커밋 시점 데이터로 돌려보기」가 불가능해진다.
- **AI 가 못 본다.** 이 저장소의 전제(AI 에이전트가 텍스트를 읽고 고친다)가 깨진다.
- **얻는 것이 지금 필요 없다.** 서버 DB 가 이기는 자리는 *여러 사람 동시 편집 · 잠금 · 권한*인데, 1인 개발엔 없다.

**언제 다시 보나** : 같이 수치를 만지는 사람이 둘 이상 생기고, 동시 편집 충돌이 실제로 아플 때.
그때도 서버 DB 대신 「구글 시트를 편집 창구로, JSON 을 커밋 원본으로」가 먼저 후보다.

### 엑셀·구글 시트는 어디에 쓰나

실무 기획자들은 밸런스 수식을 스프레드시트에서 짠다. 거기가 익숙하고 수식·그래프가 있어서다.
(출처: [Spreadsheet Tools in Game Design](https://medium.com/@urpi/spreadsheet-tools-in-game-design-57511eac68c) ·
[Practical tips on technical Game Design Documentation — Spreadsheets](https://www.gamedeveloper.com/design/practical-tips-on-technical-game-design-documentation-part-3---spreadsheets))
같은 글들이 한계도 같이 짚는다 — **구조를 강제하지 못하고, 버전 관리가 수동**이다.

그래서 권하는 자리는 **원본이 아니라 「들어오는 문」**이다.
엑셀/시트에서 수식을 짠 다음 DataTool 로 **가져오기(import)** 하고, 커밋되는 원본은 JSON 으로 둔다.
Unity 쪽에도 같은 모양의 툴이 이미 여럿 있다 (에셋스토어의 SheetForge · Scriptable Sheets 등).

### 참고할 오픈소스 — BakingSheet

C#/Unity 용 데이터시트 라이브러리. **스키마를 C# 클래스로 정의**하고 엑셀·구글 시트·CSV·JSON 을 가져와
CSV·JSON·ScriptableObject 로 내보낸다. 시트 위에 메타데이터를 안 얹는 게 특징이고,
시트끼리 참조·값 변환기·검증을 붙일 수 있다. 개발 중엔 시트, 배포 땐 JSON 만 들고 가라는 설계다.

- MIT · 별 455 · **마지막 푸시 2024-06-18** (약 2년 3개월 멈춤 — 유지보수는 사실상 잠잠하다)
- 출처: [cathei/BakingSheet](https://github.com/cathei/BakingSheet) ·
  [README](https://github.com/cathei/BakingSheet/blob/master/README.md) ·
  [OpenUPM](https://openupm.com/packages/com.cathei.bakingsheet/)

**「스키마를 코드에 둔다」는 설계 결정은 그대로 빌려올 만하다.** 라이브러리 자체를 의존성으로 쓸지는
멈춰 있는 점 때문에 메인 세션이 판단할 몫이다.

### 다국어 문자열

번역 문자열은 게임 데이터와 **다른 파일로 분리**하는 걸 권한다. 번역은 손 타는 주기도 사람도 다르다.
Unity 공식 Localization 패키지가 String Table 을 **CSV·XLIFF·구글 시트**로 내보내고 들여온다.
(출처: [Unity Localization — Google Sheets](https://docs.unity3d.com/Packages/com.unity.localization@1.2/manual/Google-Sheets.html) ·
[Unity 6 Manual — Localization](https://docs.unity3d.com/6000.3/Documentation/Manual/com.unity.localization.html))
DataTool 은 「키만 들고 있고 문자열 본문은 Localization 에 맡긴다」가 깔끔하다.

### 왜 MemoryPack 인가

- **속도** : 일반 객체 기준 System.Text.Json 대비 10배, MessagePack 대비 3배, 구조체 배열은 50~200배.
  Unity 에선 JsonUtility 대비 3~10배로 적혀 있다.
  (출처: [Cysharp/MemoryPack README](https://github.com/Cysharp/MemoryPack))
- **IL2CPP 안전** : 리플렉션이 아니라 **C# 소스 제너레이터**로 코드를 미리 만든다.
  IL2CPP 는 빌드 때 못 본 타입·메서드의 코드를 만들지 않는다 — 리플렉션에 기대는 직렬화가 위험한 이유가 이거다.
  (출처: [Unity Manual — IL2CPP limitations](https://docs.unity3d.com/6000.3/Documentation/Manual/scripting-restrictions.html))
- **암호화가 그냥 붙는다** : 결과가 `byte[]` 하나라 암호화 함수로 감싸면 끝이다.
- **Unity 6 호환** : 최소 2022.3.12f1 (소스 제너레이터로 IL2CPP 를 지원하기 위한 하한).

**MessagePack-CSharp 가 2순위인 이유** : 최근 커밋이 더 활발하고(2026-09-17), **LZ4 압축이 내장**이며,
가변 길이 정수라 파일이 더 작다. MemoryPack 은 int 가 항상 4바이트라 정수가 많은 표에선 더 커진다.
**파일 크기가 속도보다 중요하면 MessagePack 을 고른다.**
(출처: [MessagePack-CSharp](https://github.com/MessagePack-CSharp/MessagePack-CSharp))

### FlatBuffers·Protobuf 를 뺀 이유

- **FlatBuffers** : 「파일을 그 자리에서 읽어 역직렬화가 0」이 강점인데, **암호화하면 그 강점이 사라진다**
  (복호화하려면 어차피 통째로 메모리에 풀어야 한다). 스키마 파일(.fbs)과 코드 생성 단계도 늘어난다.
- **Protobuf** : 잘 돌지만 스키마를 .proto 로 또 쓴다. C# 클래스 하나로 끝나는 MemoryPack 쪽이 1인 개발에 가볍다.

### ScriptableObject 를 런타임 원본으로 안 쓰는 이유

이 저장소 규칙 10번이 이미 정했다 — **ScriptableObject 는 수치 데이터 통으로만**.
거기에 더해 실무적으로 세 가지가 걸린다.

1. **암호화가 안 된다.** 에셋을 엔진이 직접 읽는다. 중간에 낄 자리가 없다.
2. **git 에서 잘 깨진다.** `.asset` 은 텍스트 YAML 이지만 GUID 와 메타 파일이 섞여 머지가 아프다.
3. **에디터 없이 못 고친다.** AI 가 손대기 나쁘다.

**쓸 자리는 있다** : 디버그용·에디터 미리보기용으로 JSON → ScriptableObject 를 **내보내기(export)** 해 두는 건 유용하다.
(BakingSheet 도 ScriptableObject 내보내기를 지원한다.) 원본이 아니라 파생물로만 둔다.

### SQLite 를 런타임에 안 쓰는 이유

네이티브 플러그인이라 플랫폼마다 사고가 난다. IL2CPP + iOS 에서 붙지 않거나 ARM64 가 빠져 있던 사례가 보고돼 있고,
Android·WebGL 은 StreamingAssets 에서 DB 를 직접 열지 못해 결국 메모리에 통째로 올린다.
(출처: [SQLite4Unity3d](https://github.com/robertohuertasm/SQLite4Unity3d) ·
[iOS IL2CPP SQLite 연결 실패](https://forum.unity.com/threads/ios-couldnt-connect-to-sqlite-database-while-using-il2cpp.330094/) ·
[unity-sqlite-net](https://github.com/gilzoide/unity-sqlite-net))

**값어치가 있는 경우** : 데이터가 메모리에 다 못 올릴 만큼 크고(수십 MB+) 복잡한 질의가 필요할 때.
스탯·아이템·드롭 테이블 규모라면 통째로 올려 딕셔너리로 찾는 편이 빠르고 단순하다.

### 패치·핫픽스 (Addressables)

데이터를 빌드에 박지 않고 **Addressables 원격 그룹**에 올리면 앱 재배포 없이 수치를 고칠 수 있다.
1차 개발에는 과할 수 있으니 **파일 포맷만 Addressables 로 옮길 수 있게** 만들어 두면 된다 —
「바이트 배열 하나 = 테이블 한 벌」 구조면 그대로 옮겨진다.

## C. 암호화

### 먼저 — 한계를 솔직히

**클라이언트에 키가 있으면 결국 뚫린다.** 이건 의견이 아니라 구조다.
게임이 복호화할 수 있다면 = 키가 기기 안에 있다 = 찾아낼 수 있다.

- Unity 게임 해킹 안내서가 공개돼 있고, Cheat Engine 의 `Dissect Mono` 로 메모리를 뜯는다.
  AssetRipper 로 에셋을 Unity 원본 형태로 되돌린다.
  (출처: [Unity-game-hacking](https://github.com/imadr/Unity-game-hacking))
- Unity 공식 문서도 같은 말을 한다 — **사용자가 마음먹으면 결국 뽑아낸다.**
  (출처: [Unity Manual — Protecting Content](https://docs.unity3d.com/540/Documentation/Manual/protectingcontent.html))
- Unity 포럼에서 IL2CPP 암호화 지원 요청 글에도 「비싼 난독화 도구는 가짜 안심만 준다」는 반론이 달린다.
  (출처: [IL2CPP & Data Encryption](https://discussions.unity.com/t/il2cpp-data-encryption/1709129))
- 커뮤니티 결론은 한결같다 — **정말 지켜야 하면 서버에서 계산하고 클라이언트는 결과만 보여준다.**

**그래서 목표를 이렇게 잡는다** : 「못 뚫게」가 아니라
**① 메모장으로 표를 고쳐 치트하는 걸 막고 ② 출시 전 데이터를 남이 통째로 긁어 퍼가는 걸 귀찮게 만든다.**
이 정도는 AES 한 겹으로 충분히 달성된다. 그 이상은 값이 급격히 비싸진다.

### 방식 비교

| 방식 | 강도 | 무결성(위변조 검사) | 속도 | Unity 적합성 |
| --- | --- | --- | --- | --- |
| **AES-256-GCM** | 강함 | **포함** | 빠름 (하드웨어 가속) | 좋음. 단 `AesGcm.IsSupported` 확인 필요 |
| AES-256-CBC + HMAC-SHA256 | 강함 | **따로 붙여야 함** (Encrypt-then-MAC) | 빠름 | **가장 안전한 선택** — 어디서나 돈다 |
| ChaCha20-Poly1305 | 강함 | 포함 | AES 가속 없는 기기에서 유리 | .NET 기본 API 있으나 플랫폼 지원 편차 |
| XOR 난독화 | **아주 약함** | 없음 | 가장 빠름 | 「메모장 수정 막기」 정도만. 보조로만 |

**추천은 AES-256-GCM, 대안은 AES-CBC + HMAC.**
GCM 은 암호화와 「이 파일 건드렸나」 검사를 한 번에 한다. 별도 HMAC 코드가 필요 없다.
다만 .NET 문서가 **GCM 은 플랫폼 API 에 기대므로 모든 플랫폼에 있지 않고,
`IsSupported` 로 실행 시점에 확인하라**고 못 박는다.
(출처: [AesGcm 클래스](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.aesgcm) ·
[Cross-Platform Cryptography in .NET](https://learn.microsoft.com/en-us/dotnet/standard/security/cross-platform-cryptography))
Unity 6 의 IL2CPP 는 .NET Standard 2.1 만 쓴다는 점도 같이 본다.

→ **DataTool 은 GCM 을 1순위로 쓰되, `AesGcm.IsSupported == false` 면 CBC+HMAC 으로 떨어지게 짠다.**
CBC 를 쓸 땐 반드시 **암호화한 다음 그 결과에 MAC** (Encrypt-then-MAC) 순서로 한다.
(출처: [Encryption vs Compression — what order](https://www.encryptionconsulting.com/education-center/encryption-and-compression/))

### 압축과 암호화 순서 — 압축 먼저

**압축 → 암호화**가 맞다. 암호화된 바이트는 무작위처럼 보여서 압축이 안 먹는다.
CRIME/BREACH 공격 때문에 「압축 먼저」가 위험한 경우가 있지만, 그건
**공격자가 넣은 값과 비밀이 같은 스트림에 섞일 때** 이야기다.
게임 데이터 테이블은 통째로 미리 만들어 굽는 정적 파일이라 해당하지 않는다.
(출처: [Compression and Encryption Interaction](https://adhdecode.com/storage-systems/deduplication-and-compression/compression-encryption-interaction/) ·
[HN — Should you encrypt or compress first?](https://news.ycombinator.com/item?id=11994286))

MessagePack 을 고르면 LZ4 가 내장이라 압축 단계를 따로 안 짜도 된다.

### 파일 머리(헤더)를 정해 둔다

버전을 안 박아 두면 나중에 알고리즘을 못 바꾼다. 최소한 이 정도.

```
매직(4B) | 포맷버전(1B) | 알고리즘ID(1B) | nonce/IV(12 or 16B) | 본문 | 태그(16B)
```

- **매직**으로 「이 파일 내 거 맞나」를 싸게 확인한다.
- **알고리즘ID** 가 GCM/CBC 중 무엇으로 구운 파일인지 알려 준다 — 나중에 바꿔도 옛 파일이 읽힌다.
- **nonce 는 파일마다 새로 뽑는다.** 같은 키로 같은 nonce 를 두 번 쓰면 GCM 은 깨진다.

### 키 보관 — 네 단계

| 방법 | 지키는 정도 | 드는 값 | 언제 |
| --- | --- | --- | --- |
| 코드 상수 | 낮음 (문자열 뒤지면 나옴) | 거의 없음 | **1차. 여기서 시작한다** |
| 조각내 흩뿌리기 + 실행 시점 조립 | 낮음~보통 | 낮음 | 상수 쓰기 아쉬울 때 얹는다 |
| 서버에서 받기 | 보통 | 높음 (서버 필요) | 온라인 게임이거나 원격 패치를 할 때 |
| 기기에서 뽑기 (기기 고유값 파생) | 세이브 파일엔 좋음 | 보통 | **세이브 파일용. 배포 데이터엔 못 씀** |

**중요** : 기기 파생 키는 「내 세이브를 남이 못 고치게」엔 맞지만,
**모두에게 똑같이 배포되는 게임 데이터에는 쓸 수 없다** (기기마다 키가 달라지니 미리 못 굽는다).
배포 데이터와 세이브 데이터는 **키 전략이 다르다** — 이걸 섞지 않는 게 설계 요점이다.

### Unity 에셋 자체 보호 vs 데이터 파일만 암호화

| 갈래 | 방법 | 비용 |
| --- | --- | --- |
| 에셋번들/Addressables 통째로 | 커스텀 AssetBundle Provider 를 만들어 로드 직전에 복호화. 또는 암호화한 바이트를 `.bytes` 확장자로 두어 Unity 가 TextAsset 으로 다루게 한 뒤 `AssetBundle.LoadFromMemoryAsync` 로 올린다 | **높다.** Unity 공식 지원 없음. 로딩이 느려지고(메모리에 통째로) 버전 올릴 때마다 깨질 위험 |
| **데이터 파일만** | DataTool 이 구운 바이트 덩어리만 암호화. 게임 코드가 읽을 때 푼다 | **낮다.** 우리가 전부 통제한다 |

**데이터 파일만 한다.** DataTool 은 데이터 툴이지 에셋 보호 툴이 아니다.
에셋번들 암호화는 필요해지면 그때 따로 붙인다.
참고 구현: [HiKit/AddressableAESEncrypt](https://github.com/HiKit/AddressableAESEncrypt) (별 48 · 마지막 푸시 2025-02-07 ·
라이선스 표기 없음 — **읽기용 참고로만**) ·
[Unity-Technologies/Addressables-Sample](https://github.com/Unity-Technologies/Addressables-Sample) ·
[AssetBundle Encryption 토론](https://discussions.unity.com/t/assetbundle-encryption/758263)

### 실무 스튜디오는 어떻게 하나 (확인된 범위)

정리하면 **세 층**으로 나뉜다.

1. **데이터 파일 암호화 (AES)** — 가장 흔하다. 목표는 「쉬운 치트 차단」.
2. **코드 난독화 · IL2CPP** — 로직을 읽기 어렵게. Unity 의 IL2CPP 자체가 1차 방어선 역할을 한다.
3. **서버 권위(authoritative)** — 정말 중요한 수치는 클라이언트를 안 믿고 서버에서 계산한다. **이게 유일하게 확실한 방법이다.**

(출처: [Cybersecurity for Game Developers](https://dev.to/guardingpearsoftware/cybersecurity-for-game-developers-how-to-protect-your-projects-from-cyber-threats-1cb5) ·
[Secure Game Authentication — Encryption in Unity](https://dev.to/hardikojha_079/secure-game-authentication-encryption-techniques-and-their-role-in-unity-game-development-2lfj) ·
[Encrypting Game Data with Unity](https://videlais.com/2021/02/28/encrypting-game-data-with-unity/))

1인 싱글 게임이면 **1번만** 하는 게 맞다. 2·3번은 값에 비해 얻는 게 적다.

## D. 그래서 흐름은

```
엑셀/구글시트 (선택)  →  DataTool 표 편집 화면
                              ↓
                   JSON 원본 (git 에 커밋 · AI 가 읽음)
                              ↓  굽기(bake)
                   MemoryPack 바이너리
                              ↓  압축 → AES-256-GCM
                   .bin 파일 (StreamingAssets 또는 Addressables)
                              ↓
                   Unity 런타임 : 복호화 → 역직렬화 → 딕셔너리
```

곁가지로 **JSON → ScriptableObject 내보내기**를 두면 에디터에서 눈으로 보기 편하다 (원본 아님, 파생물).

## E. 확인 못 한 것

- **`AesGcm` 이 Unity 6 IL2CPP 의 각 플랫폼(Windows/Android/iOS/WebGL)에서 실제로 도는지.**
  .NET 문서의 「플랫폼마다 다르다, `IsSupported` 로 확인하라」까지만 확인했다.
  Unity 쪽에서 플랫폼별로 된다/안 된다고 못 박은 공식 문서는 못 찾았다. **실제로 빌드해 봐야 안다.**
  (WebGL 은 특히 의심스럽다 — 암호화 API 관련 문제 제보가 있다고 언급되나 내용은 확인 못 했다.)
- **MemoryPack vs MessagePack 의 실제 Unity 런타임 수치.** README 의 벤치마크만 봤다. 우리 데이터로 재 봐야 한다.
- **수만 행 JSON 을 DataTool 이 얼마나 빠르게 읽고 쓰는지.** 편집 화면 반응 속도는 실측이 필요하다.
- **GDC/NDC 발표 자료.** 이번 조사 범위에서 「데이터 파이프라인·암호화」 주제의 발표를 특정하지 못했다.
  공식 문서·오픈소스·커뮤니티 글 위주로 정리했다.
- **BakingSheet 가 멈춘 이유.** 마지막 푸시가 2024-06-18 인 것만 확인했다. 버려진 건지 「다 됐다」인지는 모른다.
- **엑셀 xlsx 읽기 라이브러리의 라이선스·성능.** 가져오기를 붙일 거면 따로 조사가 필요하다.

## F. 메인 세션이 판단할 것

1. **MemoryPack 이냐 MessagePack 이냐.**
   속도(MemoryPack) vs 파일 크기 + LZ4 내장 + 더 활발한 유지보수(MessagePack).
   → 모바일이면 크기가 중요하니 MessagePack 쪽이 유리할 수 있다.
2. **BakingSheet 를 의존성으로 쓸까, 설계만 빌릴까.**
   2년 넘게 멈춰 있다. 이 저장소의 「툴은 자기 안에서 완결」 규칙과도 견줘 봐야 한다.
3. **엑셀·구글 시트 가져오기를 1차에 넣을까.**
   없어도 돌아간다. 1차는 JSON 만, 2차에 시트 가져오기가 순서로는 맞아 보인다.
4. **암호화를 1차에 넣을까.** 굽기 단계에 「그냥 통과」와 「암호화」를 갈아 끼울 수 있게만 만들어 두고,
   실제 암호화는 나중에 켜는 방법도 있다.
5. **원본 JSON 을 「테이블별 한 파일」로 고정할지, 「행마다 파일」도 지원할지.**
   1인 개발이면 전자만으로 충분해 보인다.
6. **다국어 문자열을 DataTool 이 들고 있을지, Unity Localization 에 넘길지.**
