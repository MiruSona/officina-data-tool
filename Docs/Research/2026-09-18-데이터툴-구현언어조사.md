# DataTool 구현 언어·형태 조사 (2026-09-18)

게임 데이터(스탯·아이템·드롭 테이블)를 **표로 보고 고치고 → Unity 로 내보내고 → 암호화**하는 툴을
**무엇으로 만들까**를 조사했다. 웹 조사만 했고 아무것도 만들어 보지 않았다.

---

## 1. 추천 : 2안

| 순위 | 안 | 왜 |
| --- | --- | --- |
| **1안** | **Go 단일 실행 파일(엔진·CLI) + 브라우저 표 UI** — 데이터 원본은 사람이 읽는 텍스트 한 파일, UI 는 `go:embed` 로 넣은 웹 화면(Tabulator 또는 Glide Data Grid), 창이 필요해지면 Wails 로 감싼다 | 기존 툴들과 같은 결(Go·CGO 없음·단일 실행)이라 배포가 공짜다. **엔진(검증·익스포트·암호화)이 CLI 라 AI 에이전트가 그대로 부를 수 있고**, 표 UX 는 웹 표 라이브러리가 데스크톱 GUI 보다 훨씬 앞서 있다. 이 구조는 CastleDB 가 실제 상용 게임 개발에서 10년 넘게 쓰며 증명한 모양이다 |
| **2안(먼저 해볼 것)** | **엑셀·구글 시트를 편집기로 쓰고 Go 변환기만 만든다** | 표 편집기를 만드는 공수가 0 이다. 인디·중소 현장에서 가장 흔한 길이고 도구가 이미 널려 있다. **다만 병합·되돌리기·참조 검사가 약하고 git 에서 충돌을 못 푼다** — 이게 아프면 1안으로 간다 |

**핵심 갈림길은 「표 UI 를 직접 만들 것인가」이지 「무슨 언어인가」가 아니다.**
표 UI(수천 행 · 셀 편집 · 되돌리기 · 열 타입 검사 · 참조 걸기)는 어느 언어로 만들든 가장 비싼 부분이다.
그래서 **엔진과 UI 를 갈라 놓고, 엔진부터 만들고 UI 는 남의 것을 얹는** 1·2안을 민다.

> **버리는 안** : C#/WPF·MAUI(윈도우 전용·표 품질 대비 공수 큼), C++/Qt(라이선스·빌드 부담이 1인에게 과함),
> Python(배포가 무겁고 기존 툴 결과 다름), Unity 에디터 확장 단독(에디터를 켜야만 데이터를 만질 수 있어 AI·자동화와 상성 나쁨).

## 3. 후보별 상세

### 3-1. Go 단일 실행 파일 (1안)

- **Go 로 네이티브 GUI 는 아직 무리다.** Fyne(별 28.7k, 최근 커밋 2026-09-17)은 Go 만으로 UI 를 그리지만
  스프레드시트급 표 컨트롤이 없다. 직접 만들면 그게 툴 전체보다 크다.
- **현실적인 길은 UI 를 웹으로 두는 것이다.** 둘 중 하나.
  - (가) `go:embed` 로 HTML/JS 를 실행 파일에 넣고 로컬 서버를 띄운 뒤 브라우저로 연다. 의존성 0, 진짜 단일 exe.
  - (나) **Wails**(별 36.3k, 2026-09-18 커밋, MIT)로 감싼다. OS 내장 WebView(윈도우는 WebView2)를 써서
    Chromium 을 안 싣는다 — Tauri 와 같은 방식이고 실행 파일이 작다. 창·파일 대화상자가 필요해지면 그때 옮기면 된다.
- **표 라이브러리**는 아래 3-3 참고. 캔버스로 그리는 Glide Data Grid 나 MIT 인 Tabulator 가 후보다.
- **AI 친화가 가장 큰 이점이다.** `datatool validate` · `datatool export --unity …` · `datatool encrypt …` 처럼
  CLI 로 갈라 두면 AI 에이전트는 UI 를 안 보고도 전부 할 수 있고, 사람은 표로 본다. 같은 엔진을 둘이 나눠 쓴다.
- **위험** : Go 웹 UI 조합은 「표준 길」이 아니라 손으로 붙이는 부분이 있다. 되돌리기(undo)·복사 붙여넣기 같은
  스프레드시트 감각은 표 라이브러리가 어디까지 주느냐에 달렸다 — 고르기 전에 실제로 한 번 만들어 봐야 한다.

### 3-2. 엑셀 · 구글 시트를 편집기로 (2안)

- **가장 흔한 실무 패턴이다.** Unity 쪽만 봐도 `excel-to-unity`, `Unity-QuickSheet`, `GameDataConverter`,
  `Excel2BinaryData-Unity`, 에셋스토어의 `BG Database`·`DataLoom` 등 같은 일을 하는 도구가 계속 나온다.
  즉 **표 편집기는 아무도 새로 만들고 싶어 하지 않는다.**
- **장점** : 편집 UX 가 공짜로 최고급이다. 기획자(=사용자 본인)가 이미 쓸 줄 안다. 툴은 「읽고 → 검사하고 → 내보내는」
  변환기만 만들면 되니 Go 로 작고 깔끔하게 끝난다.
- **단점** (CastleDB 만든 쪽이 지적하는 것과 같다)
  - **버전 관리에 아주 나쁘다.** xlsx 는 바이너리라 diff·머지가 안 된다. 1인이면 덜 아프지만 AI 와 같이 고칠 땐 아프다.
  - **데이터 모델이 없다.** 열 타입·필수값·다른 표 참조(외래키)를 시트가 지켜 주지 않는다 → 검사기를 툴이 따로 다 만들어야 한다.
  - **AI 가 직접 못 고친다.** AI 는 텍스트는 잘 고치지만 xlsx 는 못 연다. (TSV/CSV 로 두면 이 문제는 풀리지만
    그러면 엑셀의 장점인 수식·서식이 사라진다.)
- **구글 시트**로 가면 공동 편집·기록은 좋아지지만 인터넷·API 키·권한이 끼고 오프라인에서 막힌다.

### 3-3. 웹(브라우저) 기반 · Electron/Tauri

- **표 라이브러리 (여기가 이 조사의 알맹이)**

  | 라이브러리 | 별 / 최근 커밋 | 라이선스 | 성격 |
  | --- | --- | --- | --- |
  | AG Grid | 15.6k / 2026-09-18 | 커뮤니티판 MIT + 유료 Enterprise | 가장 기능 많음. 대용량 가상 스크롤 강함. 쓸 만한 기능이 유료판에 몰려 있음 |
  | Handsontable | 22.0k / 2026-09-18 | **상용(개발자 1인 연 $999)**, 비상업만 무료 | 스프레드시트 감각이 가장 진짜에 가까움. 지연 로딩이 없어 대용량은 약함 |
  | Tabulator | (조회 실패) | **MIT, 유료판 없음** | 요구가 단순하고 돈이 중요할 때 실용적 |
  | Glide Data Grid | 5.3k / 2026-01-21 | MIT | 캔버스로 그려서 큰 표 스크롤이 빠름. 커밋이 8개월째 뜸함 |
  | RevoGrid | 3.4k / 2026-09-16 | MIT | 10만 행에서 메모리 214MB (AG Grid·Handsontable 1297MB) 로 가장 가벼움 |

  10만 행 벤치에서 AG Grid 60.6 FPS · Handsontable 60.9 FPS 로 **속도는 셋 다 60 FPS 를 지켰고
  차이는 메모리에서 났다.** 게임 데이터는 보통 수천 행이니 셋 다 넉넉하다 → **라이선스와 MIT 여부로 고르면 된다.**
- **포장** : Electron 은 Chromium 을 통째로 실어 80~150MB, Tauri v2 는 OS WebView 를 써서 약 5MB(최소 600KB).
  다만 Tauri 는 OS 마다 WebView 엔진이 달라 화면이 미세하게 다를 수 있다. 윈도우만 쓰면 문제 안 된다.
  **Tauri(Rust)를 쓸 바엔 같은 구조인 Wails(Go)가 이 저장소 결에 맞는다.**
- **순수 웹(포장 없이 브라우저로 열기)이 가장 싸다.** 로컬 파일 읽기·쓰기를 Go 서버가 하면 되므로
  Electron/Tauri 는 나중에 필요해지면 얹는다.

### 3-4. Unity 에디터 안 도구 (EditorWindow · UI Toolkit)

- **UI Toolkit 의 `MultiColumnListView`** 가 표를 그린다. 가상 스크롤이 있어 행이 많아도 견딘다.
  다만 「셀 편집 · 여러 칸 복사 붙여넣기 · Ctrl+Z · 열 타입 검사 · 참조 고르기」는 전부 직접 짜야 한다.
- **참고할 오픈소스** : `TableForge`(별 58, 2026-01-26 커밋) — ScriptableObject 를 스프레드시트처럼 보고 고치는
  에디터 툴. 에셋스토어에도 올라 있다. 별 수가 적어 **성숙도는 낮다**고 봐야 한다.
- **Odin Inspector**(에셋스토어, 정가 $55)는 `OdinEditorWindow` + 리스트/테이블 드로어로 에디터 창을 빨리 만들게 해 준다.
  무료 대안으로 `Alchemy` 가 거론된다. 둘 다 **툴을 대신 만들어 주는 게 아니라 만드는 품을 줄여 준다.**
- **이 길의 결정적 약점 두 가지**
  1. **AI 가 Unity 에디터를 못 본다.** 데이터를 고치려면 사람이 에디터를 켜야 한다 — 이 프로젝트 원칙과 정면으로 부딪힌다.
  2. **툴이 게임 저장소에 묶인다.** 「툴 하나 = 최상위 폴더 하나, 나중에 독립 저장소로 분리」 규칙과 안 맞는다.
- ScriptableObject 자체의 한계도 같이 지적된다 : 데이터가 Unity 에디터 안에서만 만들어지고, 순수 데이터가 아니라
  클래스 정의와 인스턴스가 필요하며, **아이템 100개면 에셋 파일 100개**라 규모를 못 견딘다.
- **결론** : 에디터 확장은 **메인 편집기가 아니라 「임포트 버튼 + 미리보기」 정도의 얇은 껍데기**로만 두는 게 맞다.

### 3-5. C# 데스크톱 (WPF · WinForms · Avalonia · MAUI)

- **Avalonia**(별 31.5k, 2026-09-18 커밋, MIT)가 이 묶음에서 제일 낫다. 2026-04 에 12 가 나왔고
  Skia 합성 렌더러로 1만 행 DataGrid 가 60 FPS 이상으로 부드럽다는 보고가 있다. WPF XAML 을 거의 그대로 옮길 수 있다.
  윈도우 밖(맥·리눅스)으로도 간다.
- **WPF** 는 윈도우 전용이고 그 밖으로 나갈 길이 없다(상용 호환 계층 Avalonia XPF 는 유료).
- **MAUI** 는 모바일·데스크톱 겸용이라 데스크톱 표 편집기에는 결이 안 맞는다. **WinForms** 는 지금 새로 시작할 이유가 없다.
- **이 묶음의 진짜 값** : C# 이니 **Unity 와 데이터 클래스를 그대로 나눠 쓸 수 있다**(같은 `.cs` 를 링크). 이건 큰 장점이다.
- **문제** : DataGrid 는 「표」지 「스프레드시트」가 아니다. 붙여넣기·되돌리기·수식 같은 감각을 직접 만들어야 하는 건
  Unity 에디터 확장과 똑같고, 공수는 웹 표 라이브러리를 얹는 것보다 훨씬 크다. GUI 라 AI 친화도 떨어진다.

### 3-6. C/C++ 데스크톱 (Qt · Dear ImGui · wxWidgets)

- **대형 스튜디오 사내 툴에서는 흔하다.** 다만 갈린다 — 엔진 툴 쪽은 wxWidgets·Qt·MFC·자체 툴킷을 쓰고,
  **Dear ImGui**(별 76.2k, 2026-09-17 커밋, MIT)는 주로 **게임 안 디버그 오버레이·인게임 에디터**에 쓴다.
  ImGui 는 원래 Media Molecule 지원으로 만들어져 자사 게임에 먼저 쓰였다.
- **ImGui 는 이 일에 안 맞는다.** 즉시 모드라 상태(선택·되돌리기·필터)를 전부 직접 들고 있어야 하고,
  스프레드시트급 셀 편집은 애초에 노린 자리가 아니다.
- **Qt 는 표 품질이 좋지만** 빌드 의존성이 무겁고 라이선스가 까다롭다. **1인 + AI 조합에 붙는 짐이 너무 크다.**
- 참고 : 게임 업계는 사내 툴 선택을 거의 공개하지 않아서 **「어느 스튜디오가 무엇을 쓴다」는 대체로 확인이 안 된다.**

### 3-7. Python (PySide · Streamlit)

- 파이프라인 변환 스크립트로는 업계에서 아주 흔하다. AI 친화도 좋다.
- 그러나 **배포가 무겁다** (런타임·의존성, PyInstaller 로 묶어도 수십 MB + 바이러스 오탐).
  Streamlit 은 표 편집이 약하고 「앱」이라기보다 대시보드다.
- **이 저장소의 다른 툴이 전부 Go 단일 실행 파일인데 혼자 Python 이면 유지보수가 갈린다.** 추천하지 않는다.

## 4. 참고할 앞선 사례 : CastleDB

**이 툴이 만들려는 것과 거의 같은 물건이 이미 있고, 상용 게임에서 오래 쓰였다.** 설계를 여기서 빌려오면 된다.

- 스프레드시트처럼 보이지만 **시트마다 데이터 모델(열 타입)이 있어 입력을 검사한다.** 아이템·NPC·스킬·테크트리용이다.
- **저장은 여러 줄로 나뉜 JSON 텍스트 한 파일.** 그래서 git 에서 diff·머지·충돌 해결이 된다 — 엑셀의 최대 약점을 정면으로 푼 지점이다.
- Haxe + Node Webkit 으로 만들어졌다(별 609, 2026-09-11 커밋, ISC). 즉 **「웹 UI + 텍스트 원본」이 원본 설계다.**
- Unity 붙이기 사례가 공개돼 있다 : `ScriptedImporter` 로 `.cdb` 를 읽어 **시트·열에서 C# 타입을 자동으로 만들어
  Assets 에 써 넣는다.** 그러면 에디터에서 타입 안전하게 데이터에 접근한다.
  → **DataTool 의 Unity 익스포트도 「데이터 + 생성된 C# 클래스」 한 쌍으로 내보내는 게 정석이다.**

---

## 5. 암호화는 언어 선택에 거의 영향이 없다

- AES 는 어느 언어에나 표준 라이브러리로 있다. **Go 는 표준 `crypto/aes`(CGO 없이) 로 끝난다.**
  Unity 쪽은 `.bytes` 확장자로 두면 `TextAsset` 으로 읽어 메모리에서 푸는 방식이 표준이다. 로딩이 조금 느려진다.
- **다만 클라이언트 암호화의 값은 게임 종류에 달렸다** — 싱글 게임의 로컬 조작 막기엔 쓸모 있지만,
  키가 클라이언트에 들어 있는 이상 작정한 사람은 푼다. 경쟁형이면 서버 권위가 답이지 암호화가 답이 아니다.
- **툴 쪽 결론** : 익스포트 마지막 단계에 `--encrypt` 를 붙이고 **키는 툴이 아니라 게임 빌드 설정에서 받게** 한다.

## 7. 메인 세션이 판단할 것

1. **표 UI 를 직접 만들 것인가, 엑셀·시트에 맡길 것인가.** 나머지는 여기서 갈린다.
   2안(변환기만)으로 시작해 아프면 1안으로 넓히는 길이 위험이 가장 낮다 — 다만 **데이터 원본 형식을 처음부터
   텍스트(CastleDB 식 여러 줄 JSON)로 잡아 두면** 나중에 편집기만 바꿔 끼울 수 있다.
2. **Wails 를 쓸 것인가, 그냥 브라우저를 띄울 것인가.** 창·파일 대화상자가 꼭 필요한지가 기준이다.
3. **표 라이브러리 고르기** — 돈을 안 쓴다면 Tabulator·Glide·RevoGrid(전부 MIT) 중에서. Handsontable 은 상용이라 사실상 탈락.
4. **Unity 쪽 산출물 모양** — 「데이터 파일 + 자동 생성 C# 클래스」로 갈지, ScriptableObject 로 구울지.
   CastleDB 사례는 전자를 민다(에셋 100개 문제 때문).
5. **Unity 에디터 확장을 얼마나 둘 것인가** — 「임포트 버튼 + 보기」만 둘지, 아니면 아예 안 둘지.
