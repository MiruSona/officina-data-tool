2026-09-18 · 웹 조사 갈래

「게임 데이터를 표로 보고 고치고 → Unity 로 내보내고 → 암호화까지」 하는 툴이 이미 있는지 샅샅이 찾았다.

**한 줄 요약** : 「표 편집기」와 「코드 생성」은 기성품이 충분히 좋다. **암호화만 우리 몫**이다.
그러니 처음부터 다 만들지 말고 **Charon 이나 Luban 을 한 번 써 보고, 모자란 곳만 우리가 채우는 길**을 먼저 재 보길 권한다.

## (1) 「NC 가 만든 비슷한 프로그램」 — 후보 둘

사용자가 기억하는 그것은 **Crema 일 가능성이 높다.** 다만 확정은 못 했다(사용자 확인 필요).

### 후보 A · Crema — 가장 유력

- 만든 곳 : **엔트리브소프트(Ntreev Soft)** — NCSoft 자회사였다(2024-02-15 문 닫음).
- 저장소 : <https://github.com/NtreevSoft/Crema> · 별 **69** · 마지막 푸시 **2022-12-07** · **MIT**
- 한 줄 설명 : "Meta data server & client tools for game development" — 게임 개발용 메타데이터 서버와 클라이언트 툴.
- 구조 :
  - **서버-클라이언트**. 통신은 WCF, 바탕 .NET Framework 4.5, 화면은 **Windows WPF**.
  - **데이터를 SVN 에 저장**한다. 그래서 「언제로든 되돌리기」「두 데이터 비교해서 합치기」가 된다.
  - **여러 사람이 동시에 고칠 수 있다** — 기획자와 프로그래머가 같이 붙는 것이 설계 목표다.
  - 엑셀 가져오기·내보내기가 있고, **C# · TypeScript · C++ 코드와 바이너리 데이터를 뽑는다.**
  - 자바스크립트로 자동화를 짤 수 있다.
- 공개 여부 : **공개(MIT)**. 다만 2022 년 이후 멈췄고 Windows·.NET Framework 에 묶여 있다.
- 이름 유래 : 에스프레소 거품 「크레마」가 쓴맛을 눅이듯, 게임 데이터 만들기를 덜 쓰게 한다는 뜻.
- 곁가지 : <https://github.com/NtreevSoft/CremaResource>, 개인 포크 `s2quake/crema`(별 1, 2021) — 설명이 "data table designer for game developing" 이다.

> 주의 : 검색하면 나오는 **`dev.cre.ma`(CREMA) 는 전혀 다른 회사의 커머스 서비스**다. 헷갈리지 말 것.

### 후보 B · 게임 리소스 스튜디오 (NC 사내 툴)

- 출처 : NC 공식 블로그 <https://about.ncsoft.com/news/article/technology-push-the-boundaries-2>
- NC 리니지M 캠프 인프라팀이 만든 **사내 전용** 툴. 공개·오픈소스 아님.
- 구조 : 「공통 포맷」 하나를 정해 두면 **엑셀 · XML · MySQL · JSON** 으로 내보내 준다.
  화면은 끌어다 놓기 방식이고, **「도큐먼트」라는 단위가 DB 의 테이블 또는 엑셀 워크시트에 해당**한다.
  기획자가 프로그래머 없이 데이터 모델을 만들고, 넣는 값을 그 자리에서 검사하고, 팀에 맞춰 준다.
- 우리가 쓸 수 있나 : **못 쓴다.** 공개 코드가 없다. 화면 구성 생각만 빌릴 수 있다.

### 못 찾은 것

- 넥슨 NDC 에서 「데이터 테이블 툴」을 다룬 발표는 **원문을 못 찾았다.** NDC Replay(<https://ndcreplay.nexon.com/>)
  가 있긴 한데 검색으로 해당 세션이 잡히지 않았다. 2026 NDC 세션 51개는 거의 AI 이야기였다.
- 넷마블·크래프톤·펄어비스·스마일게이트 쪽 공개 발표도 「데이터 테이블 툴」 주제로는 못 찾았다.
- 엔씨의 다른 공개 자료는 **게임 로그 분석**(GFIS) · **게임 데이터 오픈 API** 쪽이라 우리 주제와 다르다.

### 하나씩

**Luban** — 오늘 살아 있는 것 중 가장 크고 가장 활발하다(지난주 커밋).
「엑셀에 적으면 → 자료형 정의를 읽어 → 코드와 데이터를 뽑는다」가 전부다.
검증이 세다 : **참조 검사**(다른 표의 id 가 실제로 있나), **리소스 경로 검사**, **범위 검사**.
생성한 코드가 **리플렉션을 안 쓴다** — 그래서 코드 난독화·IL2CPP 와 충돌이 적다. Unity·Unreal·Cocos·Godot 을 다 본다.
약점 : **자기 편집기가 없다.** 엑셀이 편집기다. 다만 `luban_assistant` 라는 **엑셀 애드인**이 있어
Luban 표 데이터를 엑셀에 띄워 고치고 레코드 하나하나를 JSON 파일로 저장한다 — 여럿이 xlsx 를 동시에 고칠 때 충돌을 줄이려는 물건이다.
**Windows + Office 2016 이상만** 되고, 소스에서 직접 빌드해 .vsto 를 깔아야 한다(macOS 안 됨).
암호화는 위키·FAQ·README 어디에도 없다 — 템플릿을 직접 짜서 뒤처리로 붙이는 수밖에 없어 보인다(확인 못 함).
곁가지로 [luban_unity](https://github.com/focus-creative-games/luban_unity) 패키지와 GameFrameX 계열 통합이 있다.

**Charon** — 우리 요구에 **가장 가까운 한 벌**이다.
「표 편집기 + 코드 생성 + 엔진 붙이기」가 한 제품 안에 있다.
- 편집기가 **웹**(브라우저)과 **단독 앱** 둘 다 있고, Unity 안에도 들어간다. Unity 2021.3 이상.
- 코드 생성 : C# · TypeScript · C++(Unreal) · Haxe.
- CLI 는 무료(관대한 라이선스), Unity 플러그인은 에셋스토어 무료, Unreal 은 Fab 무료.
- 값 : Personal **무료** / Team 월 $20(3명) / Studio 월 $100(15명, REST API) / Enterprise 별도.
  **혼자 쓰면 무료**라 우리 상황에 맞는다.
- 저장소 두 개가 서로 다른 라이선스(Apache-2.0 / MIT)이고 둘 다 최근에 움직인다.
- 약점 : 데이터를 **자기 형식**으로 들고 있어 엑셀이 원본이 아니다. 암호화 언급 없음.
- 출처 : <https://www.gamedevware.com/> · <https://gamedevware.github.io/charon/unity/overview.html>

**CastleDB** — Haxe + Node Webkit 으로 만든 「구조가 있는 정적 DB」.
겉은 엑셀인데 **시트마다 데이터 모델이 있어 넣는 값을 그 자리에서 검사**한다. Enum·사용자 정의 자료형·이미지·2D 타일맵까지 한 화면에서 다룬다.
저장은 **그냥 JSON** 이라 어느 엔진에서도 읽힌다. 상용 게임(Shiro Games, Evoland 2)에 실제로 쓰였다.
약점 : Haxe 생태계다. Unity 로 붙이려면 JSON 읽는 쪽을 우리가 짜야 한다. 코드 생성 없음.
출처 : <http://castledb.org/> · <https://heaps.io/documentation/castle-db.html>

**BakingSheet** — 한국 개발자(cathei) 가 만든 것. 「표 구조를 C# 클래스로 둔다」가 핵심이다.
`Sheet` 가 표, `SheetRow` 가 한 줄. 시트끼리 참조(cross-sheet reference), `AssetPath` 로 에셋 가리키기, 값 변환기·검증기를 직접 끼울 수 있다.
Excel·Google Sheet·CSV·JSON 을 읽고 CSV·JSON·ScriptableObject 로 낸다. OpenUPM·NuGet 둘 다 있다.
약점 : **2024-06 이후 커밋이 없다.** 편집기가 없다.
이걸 바탕에 깐 파생물도 있다 — [ZBase.Foundation.Data](https://github.com/Zitga-Tech/ZBase.Foundation.Data)(별 14, 2024-09) 는 BakingSheet + C# 소스 제너레이터로 ScriptableObject DB 를 뽑는다.

**TableForge** — Unity 에디터 안에서 **ScriptableObject 를 엑셀처럼 표로 띄워 고친다.**
중첩 객체·컬렉션을 다루고, 엑셀 같은 **수식**도 되고, CSV/JSON 으로 주고받고, 복사·붙여넣기와 거르기가 좋다. Unity 2022.3 이상.
에셋스토어에도 올라와 있다(<https://assetstore.unity.com/packages/tools/utilities/tableforge-scriptableobject-management-tool-326608>).
약점 : **라이선스 파일이 없다**(GitHub API 가 라이선스를 못 읽었다) — 그대로 가져다 쓰기 전에 반드시 확인해야 한다. 별 58 로 작고 만든 사람 하나다.

**Unity-QuickSheet** — 별 1,085 로 이름값은 제일 높은데 **2021-08 에서 멈췄다.** Unity 6 는 확인 못 함. 참고만.

**LDtk 의 데이터 부분** — LDtk 는 레벨 편집기다(별 4,189, MIT, 2026-07 커밋). 우리가 볼 것은
「편집기 자체 형식 + 깨끗한 JSON 내보내기 + 자동 생성 API」라는 짜임뿐이다. 스탯 표용은 아니다.

구글 시트를 편집기로 삼는 길이다. **편집기를 안 만들어도 된다**는 것이 가장 큰 장점이고,

### Unity 공식 쪽

- Unity 가 공식으로 내놓은 「게임 데이터 테이블 편집기」는 **없다.** 표 비슷한 공식 기능은
  Localization 패키지의 **Asset Tables** 뿐이고 이건 번역·현지화 전용이다
  (<https://docs.unity3d.com/Packages/com.unity.localization@0.7/manual/AssetTables.html>).
- 공식 권장은 **ScriptableObject 로 데이터와 로직을 나눠라** 수준이다
  (<https://unity.com/how-to/separate-game-data-logic-scriptable-objects>).
- 「TableForge」라는 이름의 Unity 공식 기능은 없다. 위의 개인 에셋이거나, 이름만 같은 별개 서비스(tableforge.io)다.

### Odin Inspector 의 표 편집

- 상용(Sirenix). `[TableList]` 를 붙이면 리스트·배열을 인스펙터에 **표로 그려 준다.**
  `[HideInTables]` 로 열을 숨기고 `[TableColumnWidth]` 로 너비를 잡는다. ScriptableObject 리스트도 된다.
- 출처 : <https://odininspector.com/documentation/sirenix.odininspector.tablelistattribute>
- 우리에게 : **Unity 안에서만** 쓸 수 있고 「따로 도는 편집기」는 못 된다. 가져오기·내보내기·암호화도 없다.
  다만 **표를 그리는 손맛의 본보기**로는 좋다. 그리고 우리 프로젝트 규칙상 인스펙터 배선은 피한다.

## (5) 커뮤니티 — 주류 의견과 흔한 실패담

### 주류 의견

Unity 공식 토론방 「Tools for Managing Game Data/Content」
(<https://discussions.unity.com/t/tools-for-managing-game-data-content/892437>) 가 가장 알맹이가 있었다.

- 추천은 크게 셋으로 갈린다.
  1. **ScriptableObject** — 만들기 쉬움, 에셋 참조가 편함, Addressables 로 따로 갱신 가능.
  2. **JSON/CSV + 내가 만든 툴** — 자유롭지만 툴을 내가 다 짜야 함.
  3. **DB(SQLite/MongoDB)** — 규모가 커지면.
- 전용 툴로는 **CastleDB · articy:draft 3 · Charon** 셋이 이름이 오른다.
- 섞어 쓰는 사람이 많다 : **엑셀로 입력 → JSON 으로 저장 → ScriptableObject 로 Unity 에 넣기.**

### 흔한 실패담 · 불만

- **「자유로울수록 툴을 더 많이 짜야 한다」** — 유연한 방식을 고르면 결국 GUI 를 직접 만들게 된다.
  반대로 articy 같은 전용 툴은 편한 대신 자유가 없다.
- **툴 배우는 것 자체가 일이 된다** — 한 개발자가 articy 를 두고 "이 툴을 쓸 줄 알게 되는 것 자체가 하나의 직업 같다"
  고 했다. 혼자 만드는 사람에겐 현실성이 없다는 뜻이다.
- **Unity 인스펙터가 낡았다** — 변수 수백 개를 정리하기에 부족하다는 불만이 반복된다. 우리 툴의 존재 이유이기도 하다.
- **「정답이 없다」** — 새로 들어온 사람이 가장 헤매는 지점. 프로젝트마다 다르다는 답만 돌아온다.

### 국내

- 국내 글은 대부분 「기획자가 데이터 테이블을 어떻게 설계하나」이고, **툴 이야기는 적다.**
  팀마다 ① DB 툴로 직접 관리 ② 엑셀로 쓰고 변환해서 스크립트화 ③ 자체 툴 제작 로 갈리는데,
  **②(엑셀 → 변환) 가 가장 흔하다**고 적혀 있다.
  출처 : <http://www.gamejob.co.kr/Community/Talk/Detail?talk_Stat=13&idx=11286> ·
  <https://velog.io/@woohoosoo/기획데이터-테이블>
- 흔한 실패담 : **테이블을 잘못 고치면 게임이 아예 안 뜨거나 큰 버그가 난다** — 그래서 고친 뒤 시험·재확인이 필수라고 한다.
  → 우리 툴에 **검증기**가 왜 필요한지의 현장 근거다.

### 암호화에 대한 통념

국내 블로그·문서에서 되풀이되는 방식은 이렇다 (툴이 아니라 손으로 짜는 이야기다).

- **AES** 32바이트 키로 통째 암호화.
- Unity 에서는 **`.bytes` 확장자로 두면 TextAsset 으로 읽히므로**, 암호화한 바이트를 그대로 넣고 런타임에 푼다.
- 가벼운 **XOR** 만으로도 메모리 값 검색형 치트는 상당수 막힌다는 의견.
- 출처 : <https://docs.unity3d.com/kr/530/Manual/binarydata.html> · <https://www.ikpil.com/1344> ·
  <https://jwidaegi.blogspot.com/2019/05/unity-c-aes.html>

**어느 기성 데이터 툴도 이걸 해 주지 않는다.** 전부 「알아서 하세요」다. **여기가 우리 자리다.**

## 메인 세션이 판단할 것

1. **「직접 만든다」를 다시 재 볼 것인가.** Charon 이 무료로 우리 요구의 8할을 덮는다.
   먼저 한 번 깔아서 써 보고, 「암호화 + Unity 임포트」만 우리가 붙이는 길이 있다.
2. **엑셀을 원본으로 둘 것인가, 자체 형식을 둘 것인가.**
   - 엑셀 원본(Luban 길) : 편집기를 안 만들어도 된다. 대신 병합 충돌·서식 사고가 따라온다.
   - 자체 형식(Charon·CastleDB 길) : 편집기를 만들어야 한다. 대신 검증과 버전관리가 깔끔하다.
   - **이 갈림이 DataTool 설계의 첫 갈래다.**
3. **암호화를 어디에 둘 것인가.** 내보내기 마지막 단계에 붙일지, 저장 형식 자체를 암호화할지.
   그리고 **키를 클라이언트에 어떻게 둘 것인지** — 어차피 완벽히는 못 막으니 「어느 수준까지」를 먼저 정해야 한다.
4. **CastleDB 를 실제로 한 번 만져 볼지.** 우리 편집기 화면을 짤 때 가장 좋은 본보기다.
5. **Crema 를 사용자에게 확인받을지.** 맞다면 그 설계 문서(위키)를 더 파 볼 값어치가 있다.
